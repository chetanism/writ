# Slice SL-000 — the process itself

> Ships pre-filled by the bootstrap kit. Adjust the commands to this project's stack, delete this
> blockquote, and run it like any other slice.

## Why this slice exists

Every mechanism this process depends on — the gate, the identifier registry, the coverage ledger,
the templates — was added, in the project this was extracted from, *after* the work it was meant to
govern had already started. Eight slices made unchecked claims before there was anything to check
them, and eighteen before migration safety was enforced. None of those claims were wrong, which is
exactly the problem: nobody found out either way until the tooling arrived and the backlog had to
be reconciled by hand.

So the process is the first slice, and it is a real slice: it has acceptance criteria, a demo, and
a definition of done. **It ends with one requirement carried the whole way** — declared in a
specification, claimed in this work order, annotated in a test, and shown green in the generated
ledger. That demonstrates the machinery rather than asserting it.

## Decisions this slice makes

| Decision | Choosing | Over | ADR |
|---|---|---|---|
| Where the traceability check runs | A step in the gate, and a test in the project's own suite | A separate scheduled job | — |
| What the gate is | The commands agreed at bootstrap, run as separate CI steps | One aggregate command | — |
| Pre-commit hooks | None | A hook mirroring the gate | — |

The gate steps stay separate in CI so a red cross names the thing that broke. There are no
pre-commit hooks: the gate is CI, and a hook that re-runs the same checks more slowly is how people
learn to pass `--no-verify`.

## Acceptance criteria

1. The gate runs locally and in CI, as separate steps, and every step passes on the empty project.
2. A docs-only pull request still gets its traceability check, and does not block waiting for a
   workflow that will never run.
3. `python3 scripts/test_ledger.py` passes.
4. `python3 scripts/ledger.py check` exits 0 against the committed tree.
5. `canon/process/COVERAGE.md` is committed, and hand-editing it makes the check fail.
6. A test name annotated with a registered family but an undeclared number fails the check, naming
   the file and the identifier.
7. A work order naming an ADR that does not exist fails the check.
8. A work order whose demo section is missing, empty, or carries a placeholder identifier fails the
   check.
9. The generated queue block in `SLICE-QUEUE.md` lists every work order in dependency order, and
   the prose around it survives regeneration.
10. `DoD-7` reads as satisfied in the ledger, proven by a test in this project's own suite.
11. The requirement detail track is wired but empty: `canon/process/requirements/` holds its
    `README.md` and nothing else, `COVERAGE.md` carries the detail section, and a file quoting a
    requirement in anything but the specification's own words fails the check.
12. <Where the tracker is GitHub:> the labels `phase:<letter>` for every phase in
    `scripts/ledger.config.json` and `size:S`, `size:M`, `size:L` exist, so an issue opened at a
    claim never fails on a missing label; and this slice's own issue exists, with this file as its
    body, before the branch does. <Delete this criterion if no tracker was configured.>

## Demo

### Script

```bash
# 3 — the tool's own suite
python3 scripts/test_ledger.py

# 4, 5 — generate, then verify
python3 scripts/ledger.py
python3 scripts/ledger.py check     # exit 0

# 5 — a hand-edited ledger is caught
printf '# edited\n' >> canon/process/COVERAGE.md
python3 scripts/ledger.py check     # exit 1: "is stale"
git checkout -- canon/process/COVERAGE.md

# 1 — the gate, as CI runs it
<the gate commands, one per line>

# 10 — the requirement carried end to end
grep -n 'DoD-7' canon/process/COVERAGE.md

# 11 — the detail track's one rule, demonstrated rather than asserted
grep -n 'Requirement detail' canon/process/COVERAGE.md

# 12 — the labels, and this slice's own issue
gh label list | grep -E '^(phase|size):'
gh issue view "$(grep '^issue:' canon/process/work-orders/000.md | awk '{print $2}')" --json title -q .title
```

Expected: the check exits 0 on the committed tree and 1 on the edited one, the `DoD-7` row carries
a mark of `●` with the test name beside it, `COVERAGE.md` carries a *Requirement detail* section
reading zero files — the track installed and correctly empty — and the label list and the issue
title come back naming this slice.

**Criterion 11's second half is proven by the tool's own suite**, not by hand: writing a paraphrased
detail file into this repository to watch it fail leaves a wrong file behind for somebody to find.
`test_a_paraphrased_requirement_fails` in `scripts/test_ledger.py` is the demonstration, and step 3
above runs it.
